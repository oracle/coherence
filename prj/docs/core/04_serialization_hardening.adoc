= Serialization Hardening (SER-01)
:toc: left
:toclevels: 4
:sectnums:

This document describes Coherence serialization hardening, the secure defaults
introduced by SER-01, and the migration steps for applications that exchange
application classes across Coherence wire boundaries.

== Overview

SER-01 makes Coherence able to fail closed for common deserialization entry
points. It adds bytecode deny-list checks, JEP-290 filter enforcement, strict
POF type handling, dynamic class-definition validation, generated application
allowlists, security-mode-aware defaults, and per-boundary telemetry.

The compatibility model has two independent axes:

* `coherence.mode` remains the released runtime/license mode switch. It is not
  the global security-hardening opt-in.
* `coherence.security.mode` controls the compatibility-sensitive SER-01
  hardening gates. When unset, or set to `compatibility`, Coherence preserves
  prior-patch compatibility. Set `-Dcoherence.security.mode=hardened` to opt in
  to the hardening-on posture.

=== Why not JEP-290 alone?

`java.io.ObjectInputFilter` (JEP-290) is a transport-level filter wired to
`ObjectInputStream`. Coherence's dominant wire formats (POF, `ExternalizableLite`,
`PortableObject`) bypass `ObjectInputStream` entirely, so a JEP-290 filter alone
would silently miss the majority of deserialization traffic. SER-01 also needs
the same allowlist to drive three distinct gates -- class allowlist on
deserialization, lambda-bytecode acceptance, and remote-execution policy -- and
to compose across many modules at build time with annotation-driven generation.
JEP-290's single allow/reject bit and flat filter string cannot express that.
Coherence therefore uses `security-config.xml` as the source of truth, has every
wire-format reader consult it, and registers a JEP-290 filter that delegates
back to the same allowlist for the paths that do run through `ObjectInputStream`.
JEP-290 is a hook, not a substitute, and customer-supplied `jdk.serialFilter`
settings still compose normally for non-Coherence streams.

== Compatibility

`coherence.security.mode` controls how SER-01 gates are applied while
applications migrate to generated `security-config.xml` and explicit
remote-executable classification.

|`false`

|`hardened`

== Quick Migration Guide

For an existing application:

* Apply the patch with the existing `coherence.mode` value. Leave
  `coherence.security.mode` unset during the rolling upgrade so the cluster
  keeps prior-patch compatibility.
* Add the Maven or Gradle security-config generation step to every application
  artifact that sends filters, processors, extractors, aggregators, or other
  application payload classes over Coherence services.
* Annotate application payload types with `@Remote.Allowed` or `@PortableType`,
  rebuild, and verify that each artifact contains
  `META-INF/coherence/security-config.xml`.
* Watch `coh.executable.policy_check{result=would_reject}` in compatibility
  security mode and annotate or XML-list every remote executable class that
  appears there.
* After the full deployment is upgraded and the shadow telemetry is clean, test
  client/server workflows with `-Dcoherence.security.mode=hardened`.
* Enable `coherence.security.mode=hardened` only after all members and clients
  that need to participate in the hardened workflow are ready.

Applications that skip this migration will most commonly see two
`SecurityException` reasons at runtime: `security-config-missing` when an
application payload class is not in any generated allowlist, and
`dynamic-remote-denied-by-mode` when a DYNAMIC lambda is received while
security mode is hardened and unauthenticated dynamic remote payloads resolve
to `deny`. Both are documented in <<Error Message Reference>>.

== Runtime Modes

Coherence runtime mode is selected by the `coherence.mode` system property.
The released values are `eval`, `dev`, `development`, `prod`, and
`production`. When `coherence.mode` is unset, Coherence defaults to `dev`.
Blank, unknown, `legacy`, and `legacy-compatibility` values fail fast.

Runtime mode controls the released license/runtime mode behavior. It does not
enable the compatibility-sensitive SER-01 hardening gates.

Security mode is selected by the `coherence.security.mode` system property.
Supported values trim whitespace and compare case-insensitively:

* unset or `compatibility` keeps the compatibility-sensitive hardening gates
  disabled by default and emits bounded shadow telemetry where available.
* `hardened` enables the compatibility-sensitive hardening gates.

Blank, unknown, shorthand, and boolean-style values such as `true`, `false`,
`on`, `off`, `enabled`, or `disabled` fail fast. The removed pre-release
`coherence.security.hardened` property is not an alias.

== Build-time Allowlist Generation

The build-time generator scans compiled classes in the current artifact. It
does not scan dependency jars. Each jar that contributes wire payload types
should generate and package its own `META-INF/coherence/security-config.xml`.

=== Maven

The `security-config-maven-plugin` goal is named `generate` and is bound to
`process-classes` by default.

[source,xml]
----
<plugin>
  <groupId>com.oracle.coherence</groupId>
  <artifactId>security-config-maven-plugin</artifactId>
  <version>${coherence.version}</version>
  <executions>
    <execution>
      <id>generate-security-config</id>
      <phase>process-classes</phase>
      <goals>
        <goal>generate</goal>
      </goals>
    </execution>
  </executions>
</plugin>
----

Set `-Dcoherence.security-config.skip=true` to skip generation for a build.

=== Gradle

The Coherence Gradle plugin registers the `securityConfig` task when the Java
plugin is applied.

[source,groovy]
----
plugins {
    id 'java'
    id 'com.oracle.coherence.gradle.plugin' version coherenceVersion
}

securityConfig {
    processTestClasses = false
}
----

Set `processTestClasses = true` to also generate
`securityConfigTest` output for test classes.

=== Annotations

Use `com.tangosol.util.function.Remote.Allowed` for application classes that
may legitimately cross a wire-deserialization boundary as polymorphic
payloads.

At type level, `@Remote.Allowed` includes the annotated class and, by default,
its declared nested types. Set `recursive = false` to include only the
annotated class:

[source,java]
----
// Generates allowlist entries for MyType AND MyType.Nested.
@Remote.Allowed
public class MyType
    {
    static class Nested {}
    }

// Generates an allowlist entry for MyType only; Nested is excluded.
@Remote.Allowed(recursive = false)
public class MyType
    {
    static class Nested {}
    }
----

At package level, add `@Remote.Allowed` to `package-info.java`. The default
includes classes in that package and subpackages; `recursive = false` limits
generation to the package itself.

`com.tangosol.io.pof.schema.annotation.PortableType` also generates allowlist
entries. A class does not need both annotations unless your source code uses
both concepts for clarity.

== Generated `security-config.xml`

The generated artifact is `META-INF/coherence/security-config.xml`. At member
start, Coherence loads every such resource visible to the thread context class
loader, validates each resource against `coherence-security-config.xsd`, and
merges the allowed class names into a single runtime allowlist. A malformed
or invalid resource fails member startup and names the offending URL. The
schema is shipped as `coherence-security-config.xsd` in the Coherence jar.

A generated file looks like this:

[source,xml]
----
<?xml version="1.0" encoding="UTF-8"?>
<security-config xmlns="http://xmlns.oracle.com/coherence/coherence-security-config">
  <allowed-classes>
    <class name="com.acme.billing.InvoiceFilter"       source="@Remote.Allowed"/>
    <class name="com.acme.billing.InvoiceProcessor"    source="@Remote.Allowed"/>
    <class name="com.acme.billing.model.Invoice"       source="@PortableType"/>
    <class name="com.acme.billing.util.MoneyExtractor" source="@Remote.Allowed(package)"/>
  </allowed-classes>
</security-config>
----

Each jar on the runtime classpath contributes its own
`META-INF/coherence/security-config.xml`; the runtime unions all of them
into a single allowlist. This means multi-module applications do not need a
single curated file - each module that sends wire payload classes ships its
own generated resource. A class that is not listed in any generated file and
is not added via `coherence.serialization.allowed` is rejected at the gate.

[NOTE]
====
"Wire payload classes" means more than the obvious entry processors,
filters, aggregators, and POF data types. Any class whose state crosses a
Coherence wire boundary is subject to the allowlist gate, including classes
captured by the closure of a serialized lambda. If your code writes
`cache.invokeAll(filter, entry -> doSomething(entry, helper))` and `helper`
is an instance of `com.acme.PricingHelper`, then `PricingHelper` is part of
the lambda's serialized state and must be allowlisted on the receiver. The
typical fix is to annotate the helper class with `@Remote.Allowed` or apply
a package-level annotation. After upgrade, the most common
`security-config-missing` rejections come from such capturer classes rather
than from obvious payload types.
====

== Lambda Serialization

Coherence serializes Java lambdas in one of two representations. STATIC
lambda serialization sends a symbolic reference to a compiled lambda class
that already exists on both sender and receiver; the receiver resolves it by
name. DYNAMIC lambda serialization synthesizes bytecode on the sender and
ships it to the receiver, which defines the class on arrival. DYNAMIC is
Coherence's default and recommended mode because it avoids lockstep
class-version coordination: a new lambda can flow from an upgraded sender to
an older receiver without both sides first deploying the same compiled
class.

When `coherence.security.mode=hardened`, the DYNAMIC lambda gate denies
wire-supplied bytecode from unauthenticated peers before class definition
unless `coherence.remote.dynamic.unauthenticated=allow` is set. Applications
that opt in to hardened mode have two supported migration paths:

* Set `-Dcoherence.remote.dynamic.unauthenticated=allow` (the recommended
  path). This preserves DYNAMIC lambda serialization and the rolling-upgrade
  ergonomics that make it Coherence's default. It is a long-term option, not
  deprecated; a future Coherence release will layer subject-aware permission
  checks on top of this path. Monitor rejection telemetry on the
  `site=lambda` counter to confirm traffic shape after enabling.
* Switch to STATIC by setting `-Dcoherence.lambdas=static`. This avoids
  wire-supplied bytecode entirely but couples every sender and receiver to
  the same compiled lambda class: every producer and consumer must redeploy
  the same code version before traffic flows. This is appropriate only for
  deployments that already manage lockstep rolling upgrades; it trades
  upgrade ergonomics for wire-bytecode minimisation.

== Remote Executable Objects

Remote executable objects are application classes whose methods Coherence may
invoke on behalf of a remote request.

=== What Counts As An Executable

* Processors — `InvocableMap.EntryProcessor` implementations that run against
  cache entries.
* Aggregators — `InvocableMap.EntryAggregator` implementations that compute
  server-side aggregate results.
* Invocables — `Invocable` implementations submitted to the
  `InvocationService`.
* Filters — `Filter` implementations evaluated against cache, query, topic,
  REST, or gRPC data.
* Value extractors — `ValueExtractor` implementations that read values during
  server-side filtering, sorting, indexing, or projection.
* Comparators — `Comparator` implementations used for server-side ordering.
* Triggers — `MapTrigger` implementations installed to run during cache
  mutation.
* Server-side event interceptors — `EventInterceptor` implementations that
  run in the cluster when matching events fire.
* `coherence-concurrent` tasks / callables / runnables — executable work
  submitted through the Coherence concurrent APIs.

Client-installed `MapListener`s are routed, not invoked, on the server; they
do not require `@Remote.Executable`. A listener that additionally implements
`MapTrigger` is governed by the `MapTrigger` rule.

=== The Annotation

[source,java]
----
@Remote.Executable
public class PriceAdjustmentProcessor
        implements InvocableMap.EntryProcessor<String, Order, Void> { ... }
----

`@Remote.Executable` has CLASS retention and is class-level only. It implies
`@Remote.Allowed`: a class that is executable is also a class the receiver may
deserialize. The build-time generator emits a single entry in
`security-config.xml` with `source="@Remote.Executable"` and
`executable="true"`. At runtime, the security-config reader adds that class to
`executableFqns()` as well as `allowedFqns()`.

=== XML Alternative

You can also author the same classification by hand in
`META-INF/coherence/security-config.xml`:

[source,xml]
----
<class name="com.example.PriceAdjustmentProcessor"
       source="@Remote.Executable"
       executable="true"/>
----

Runtime merge semantics are the same as generated allowlist entries: Coherence
unions every visible classpath source into one view. See
<<Generated `security-config.xml`>> for the full merge story.

=== InvocationService

When security hardening disables the Coherence*Extend `InvocationService`
proxy by default, operators who intentionally expose remote invocation can set
`coherence.invocation.enabled=true` or configure
`<proxy-config><invocation-service-proxy><enabled>true</enabled></invocation-service-proxy></proxy-config>`.
The system property overrides operational configuration when both are present.

When the proxy is enabled, every remote `Invocable` submitted through Extend is
checked by `RemoteExecutablePolicy` before `InvocationService.query(...)`
executes it and before any delegated `PriorityTask` scheduling, timeout, or
cancellation callback can run. The invocable class must carry
`@Remote.Executable` or appear with `executable="true"` in merged
`security-config.xml`. Cluster-internal `Invocable` dispatch is not gated by
the Extend proxy flag.

If the proxy is disabled, the server log records
`InvocationService proxy is DISABLED in <mode> mode by policy` once at proxy
startup, while the client receives the same generic service-unavailable shape
used for an unbound Extend receiver. The wire response intentionally does not
name the policy decision. See the Coherence security guide section "Securing
Extend Client Connections" for Extend authentication setup.

=== MethodInvocationProcessor / ScriptProcessor

`MethodInvocationProcessor` and `ScriptProcessor` are built-in
`EntryProcessor` implementations that execute behavior described by their
serialized state. Both classes are `final`, annotated with
`@Remote.Executable`, and checked by `RemoteExecutablePolicy` before their
dynamic-remote gates run.

When `coherence.security.mode=hardened`, both processors are denied by default
unless `coherence.remote.dynamic.unauthenticated=allow` is set. With
`coherence.security.mode` unset or set to `compatibility`, the dynamic-remote
mode gate allows them by default while preserving hard-floor deny-list checks.
The same property therefore controls unauthenticated DYNAMIC lambda bytecode,
reflective method invocation through `MethodInvocationProcessor`, and script
evaluation through `ScriptProcessor`.

`MethodInvocationProcessor` also applies the lambda bytecode deny-list before
reflection. The supplier class, the runtime target class, and the
`targetClass#methodName` pair are each checked against
`META-INF/coherence/lambda-bytecode-denylist.txt` and extension resources such
as `META-INF/coherence/lambda-bytecode-denylist.d/*.txt`. Entries such as
`java.lang.Runtime` and `java.lang.System#exit` are hard floors in every
security mode. When a processor targets an absent cache entry, the
supplier class is checked first, but the supplier is not executed and the
entry is not populated until the dynamic-remote mode gate allows MIP.

`ScriptProcessor` runs scripts in the singleton Graal `Context` with explicit
host access. `allowAllAccess(true)` is not enabled. Host class lookup rejects
deny-listed classes, and loadable deny-listed classes are also blocked through
Graal `HostAccess.denyAccess(...)`. These HostAccess checks are hard floors in
every mode.

=== MapTrigger Remote Install and Removal

Remote `MapTrigger` installation and removal through Coherence*Extend are
checked before the listener is registered with or removed from the storage
tier. The trigger class must carry `@Remote.Executable` or appear with
`executable="true"` in merged `META-INF/coherence/security-config.xml`;
unannotated trigger classes are rejected in hardened security mode and shadowed
in compatibility security mode.

After the class policy check, dynamic trigger classes use the same mode gate as
DYNAMIC lambdas, `MethodInvocationProcessor`, and `ScriptProcessor`. Hardened
security mode denies dynamic trigger installation by default unless
`coherence.remote.dynamic.unauthenticated=allow` is set. Compatibility mode
permits dynamic trigger installation by default while emitting
`result=would_reject` shadow telemetry where the hardened policy would reject.

Classes declared in cache configuration remain server-trusted and are not
blocked at startup. Coherence logs a WARN for each unannotated declared
`MapTrigger` or `EventInterceptor` class, de-duplicated by class name and kind,
so operators can classify those classes before allowing equivalent remote
installs. The Slice C audit did not find a remote-supplied `EventInterceptor`
install path; interceptor coverage is therefore limited to this startup
advisory.

=== Topic Subscriber Filter / Extractor Install

Remote topic subscriber group and subscriber creation through Coherence*Extend
and gRPC are checked before the subscriber metadata is installed on the storage
tier. Subscriber filters use `OperationReason.EVALUATE_FILTER`; subscriber
extractors and converters use `OperationReason.EXTRACT`; both publish
`role=TOPICS` in telemetry. The filter or extractor class must carry
`@Remote.Executable` or appear with `executable="true"` in merged
`META-INF/coherence/security-config.xml`. Unannotated classes are rejected in
hardened security mode and shadowed in compatibility security mode.

Coherence also walks shipped topic subscriber containers that can hide nested
executable state before install and again during persisted replay. This
includes filter wrappers such as `ArrayFilter`, `ExtractorFilter`,
`LimitFilter`, and `FilterWrapper`; extractor wrappers such as
`ConditionalExtractor`, `CollectionExtractor`, `KeyExtractor`, fragment
extractors, and transaction wrappers; comparator wrappers such as
`ExtractorComparator`, `ChainedComparator`, and `SafeComparator`; and
script-backed subscriber filters and extractors. Each nested class is checked
with topic subscriber telemetry and replay-drift handling. Customer-defined
composites with opaque fields are not inspected reflectively; annotate or
allowlist the composite class and any nested classes exposed through the
built-in containers.

Dynamic or lambda-shaped subscriber filter and extractor classes use the same
dynamic remote mode gate as DYNAMIC lambdas, `MethodInvocationProcessor`,
`ScriptProcessor`, and remote `MapTrigger` installs. Hardened security mode
denies dynamic subscriber metadata by default unless
`coherence.remote.dynamic.unauthenticated=allow` is set. Compatibility security
mode permits dynamic subscriber metadata by default while emitting
`result=would_reject` shadow telemetry where the hardened policy would reject.

Persisted subscriber metadata is rechecked when topic subscription metadata is
activated from persistence. The
`coherence.topics.persisted.policy-drift` property controls how Coherence
handles metadata whose class was valid at install time but is no longer
executable at replay time:

* `reject` refuses the replayed subscription and emits
  `sub_reason=replay_drift`.
* `warn-allow` emits a deduped WARN for the drifted class and allows replay.

The default is `reject` in hardened security mode and `warn-allow` in
compatibility security mode. An explicit `reject` value fails closed in both
security modes. Operators should use
`warn-allow` only as a migration bridge while annotating the affected
filter/extractor classes, regenerating `security-config.xml`, and redeploying
the owning artifacts.

Cache-config-declared topic subscriber advisory logging is deferred. The topic
scheme bootstrap paths currently do not materialize the declared filter or
extractor instances early enough to emit a startup advisory without moving
topic subscription realization. Remote topic subscriber installs and persisted
replay rechecks are still enforced as described above.

=== Cache Data-Plane Processor / Aggregator / Filter / Extractor / Comparator Install

Remote `NamedCache` data-plane operations through Coherence*Extend, REST, and
gRPC are checked after the wire payload or registry alias resolves to a
concrete executable object and before dispatch to the storage tier. Entry
processors use `OperationReason.PROCESS_ENTRY`; aggregators use
`AGGREGATE`; filters use `EVALUATE_FILTER`; value extractors use `EXTRACT`;
comparators use `COMPARE`. Telemetry publishes `role=EXTEND_PROXY`,
`role=REST`, or `role=GRPC` depending on the transport.

The processor, aggregator, filter, extractor, or comparator class must carry
`@Remote.Executable` or appear with `executable="true"` in merged
`META-INF/coherence/security-config.xml`. Unannotated classes are rejected in
hardened security mode and shadowed in compatibility security mode. Dynamic,
lambda-shaped, or script-backed cache data-plane executables also pass through
the dynamic remote mode gate: hardened security mode denies them by default
unless `coherence.remote.dynamic.unauthenticated=allow` is set; compatibility
security mode permits them by default while emitting `result=would_reject`
shadow telemetry where the hardened policy would reject. The shared script
gate covers `ScriptProcessor`, `ScriptFilter`,
`ScriptValueExtractor`, and `ScriptAggregator`; the check runs at remote
install time where the transport exposes the script object and again directly
before script execution or delegate creation.

Coherence also walks the built-in composite containers that can hide nested
executables. This includes processor wrappers such as `CompositeProcessor`,
`ConditionalProcessor`, asynchronous / priority processor wrappers,
`ExtractorProcessor`, `PropertyProcessor`, and `UpdaterProcessor`; aggregator
wrappers such as `CompositeAggregator`, `GroupAggregator`, `ReducerAggregator`,
asynchronous / priority aggregators, and `TopNAggregator`; filter wrappers such
as `ArrayFilter`, `ExtractorFilter`, `LimitFilter`, `MapEventTransformerFilter`,
and `WrapperQueryRecorderFilter`; extractor
wrappers such as `ConditionalExtractor`, `CollectionExtractor`,
`DeserializationAccelerator`, and the fragment
extractors; and comparator wrappers such as `ExtractorComparator`,
`ChainedComparator`, and `SafeComparator`. Comparator payloads that are also
`ValueExtractor` instances, such as `KeyExtractor`, `ChainedExtractor`,
`ConditionalExtractor`, `CollectionExtractor`, and other `AbstractExtractor`
subclasses, are routed through the extractor cascade as well as the comparator
gate; this also applies when they are wrapped by `SafeComparator`,
`InverseComparator`, or `EntryComparator`.
`ValueManipulator` and `ValueUpdater` instances nested inside property and
updater processors are treated as executable mutation state under the
processor install check. Each cascaded class records its own policy telemetry
event. Customer-defined composites with opaque fields are not inspected
reflectively; annotate or allowlist the composite class and any nested classes
that are exposed through the built-in containers above.

REST default processor and aggregator factories preflight the configured class
before invoking its constructor. REST resources still check the produced
processor or aggregator instance before dispatch so nested cascade checks are
not lost. Custom REST `ProcessorFactory` and `AggregatorFactory`
implementations remain a trusted compatibility boundary: Coherence cannot
preflight arbitrary factory side effects before the custom factory chooses to
construct or return an executable object.

To migrate an application, identify each rejected or would-reject class,
annotate the supported remote executable type with `@Remote.Executable` or add
an `executable="true"` entry to generated security config, redeploy the owning
jar, and rerun the workload with `-Dcoherence.security.mode=hardened`. For REST
registry entries, classify the registry factory output. For CohQL queries and
gRPC bytes-based requests, classify the concrete filter, comparator, extractor,
aggregator, or processor class that is sent by the client.

=== Coherence Concurrent Executor

Coherence Concurrent executor submissions are checked before task execution,
scheduling, executor selection, result collection, completion callbacks, and
subscriber callbacks. Submitted `Task`, `Callable`, `Runnable`,
`ExecutionStrategy`, `Task.Collector`, completion predicate, completion
runnable, and `Task.Subscriber` classes must carry `@Remote.Executable` or
appear with `executable="true"` in merged
`META-INF/coherence/security-config.xml`. Enforcement telemetry uses
`OperationReason.CONCURRENT_TASK` and `role=CONCURRENT`.

The concurrent gate also walks shipped executor wrappers that can carry nested
callback state. `CallableTask`, `RunnableTask`, `RunnableWithResultTask`,
scheduled task wrappers, and `CronTask` gate their nested callable, runnable,
or task state after the task-manager subject is available. `CronTask` gates
both the original and current task. `StandardExecutionStrategy` gates its
candidate predicate, and `ConditionalCollector` gates its predicate and nested
collector. Concurrent cache-processor wrappers such as `LocalOnlyProcessor`
and `ClusteredTaskManager.ChainedProcessor` gate their nested processors before
they can invoke them. Built-in predicate wrappers such as
`Predicates.not(...)` and typed composites such as `Predicates.and(...)` are
unwrapped and their nested predicates are checked before use. Value-style
predicate wrappers gate nested payloads that could otherwise dispatch
application code through `equals(...)` or `toString()`: unsafe
`Predicates.equalTo(...)` values, non-built-in `Predicates.has(...)`
registration options, and non-JDK `Predicates.onException(...)` throwables are
checked before the predicate can run. Common scalar values, built-in
registration options, exact product `Member` registration metadata, and
bootstrap `java.*` throwables remain data-only. Crafted or non-product nested
members inside `Predicates.has(Member.of(...))` are checked before comparison.
`ValueTask` is gated as a task, but its value is result data and is not treated
as an executable callback merely because it implements a callback interface.
Task properties, task options, execution plans, retained results, and tracing
context are data-only for this gate.

Local member submissions capture the current caller `Subject` as advisory gate
context and serialize it with `ClusteredTaskManager` at POF index `20` and as a
final appended ExternalizableLite field. Remote-client submissions through
remote cache services, including `RemoteExecutor` client paths, serialize a
`null` subject; client JVM subjects are not authorization-bearing. The subject
is not used with `Subject.doAs(...)` and does not grant per-subject execution
permission.

The `ConcurrentProxy` Extend service uses the existing
`coherence.concurrent.extend.enabled` property with a security-mode-aware
default: enabled in compatibility security mode and disabled in hardened
security mode. A disabled proxy logs the resolved runtime mode, security mode,
property/config source, and enabled state at startup, plus a startup WARN in
hardened mode naming the override property. Clients still see a generic
service-unavailable shape rather than policy-specific wire text.
Cluster-internal executor use is independent of this proxy switch.

=== Functional-Interface Lambda Targets

A lambda target is the functional interface named by a serialized lambda. For
example, a lambda sent as a `Remote.Function` declares
`com.tangosol.util.function.Remote$Function` as its functional-interface
target; the generated lambda class is a separate implementation detail.

Coherence pre-checks that functional interface before it runs the lambda
bytecode scanner. The target check answers "may this receiver materialize a
lambda for this API surface?" with a constant-time lookup in merged
`security-config.xml`. The bytecode scanner still answers the separate
question "does this wire-supplied bytecode contain denied references or
unsupported shape?" Both checks apply; a target allowlist entry does not
disable bytecode scanning.

To allow a custom serializable functional interface as a remote lambda target,
annotate the interface with `@Remote.Executable` and ensure it also carries
`@FunctionalInterface`:

[source,java]
----
@FunctionalInterface
@Remote.Executable
public interface PriceFunction
        extends java.io.Serializable
    {
    BigDecimal apply(Order order);
    }
----

The build-time scanner emits:

[source,xml]
----
<class name="com.example.PriceFunction"
       source="@Remote.Executable"
       lambda-target="true"/>
----

You can also author that XML entry by hand. In that case the entry must name
the functional interface, not the generated lambda implementation class.

Unannotated functional interfaces are denied in hardened security mode before
lambda bytecode is materialized. In compatibility security mode, allowlist and
lambda-target enforcement are disabled; use
`-Dcoherence.security.mode=hardened` in pre-production to validate
lambda-target readiness before migration. The supported migration is to
annotate the functional interface or add a manual `lambda-target="true"` entry
to the artifact that owns it.

When the target pre-check rejects a lambda, the reason is
`REASON_LAMBDA_TARGET_NOT_ALLOWED` and the operator-visible reason string is
`lambda-target-not-allowed`. Pre-GA adopters who previously relied on custom
serializable functional interfaces should rebuild those artifacts with
`@Remote.Executable`, verify the generated `security-config.xml`, and redeploy
receivers before sending lambdas that target the new interface.

=== Migration

`@Remote.Executable` covers two distinct cases that have different
runtime-enforcement timelines in 26.04:

* *Functional interfaces* annotated with `@Remote.Executable` are enforced
  today when security mode is hardened. Lambdas that target an unannotated
  functional interface are rejected with `lambda-target-not-allowed` before
  bytecode is materialized. Migrate by annotating every custom serializable
  functional interface used as a remote lambda target and rebuilding the
  artifact that owns it. See <<Functional-Interface Lambda Targets>>.
* *Concrete executable classes* (entry processors, aggregators, invocables,
  filters, value extractors, comparators, triggers, server-side event
  interceptors, `coherence-concurrent` tasks) are classified by the build
  in 26.04. Runtime enforcement covers the CACHE-01 remote execution sinks
  described above. Classify executable classes now, regenerate
  `security-config.xml`, and use
  `coh.executable.policy_check{result=would_reject}` shadow telemetry to
  drive the migration; see <<Telemetry>>.

In both cases the build pipeline is the same. Rebuild every artifact that
owns an executable class or functional interface; the
`security-config-maven-plugin` and the Gradle `securityConfig` task pick up
the annotations automatically.

=== Why `@Remote.Executable` And Not Just `@Remote.Allowed`?

`@Remote.Allowed` answers "can this class be deserialised on the server?";
`@Remote.Executable` answers "may the server invoke its methods on behalf of
a remote request?" The latter is a strict subset and deserves an explicit
opt-in so that adding a class to the deserialisation allowlist does not
silently grant it execution privileges.

== Error Message Reference

SER-01 rejection reasons fall into four families. When debugging a failing
deployment, identify the family first, then locate the specific row in the
table below.

* *Missing allowlist* — `security-config-missing`, `ClassIdentity package is
  not allowed`, `unknown user type`, `Deserialization of class ... was
  rejected`. The class is not known to the receiver; fix by annotating and
  regenerating, or by registering with POF.
* *Remote execution policy* — `dynamic-remote-denied-by-mode`,
  `method-invocation-denied-by-mode`, `script-eval-denied-by-mode`,
  `lambda-target-not-allowed`, `class-name-on-denylist`,
  `method-on-denylist`. A lambda-shaped payload, MIP reflection request, or
  script request was refused by mode policy, target-interface policy, or by
  the explicit deny-list.
* *Bytecode shape* — `bytecode-references-gadget`, `native-method-declared`,
  `dynamic-class-forname`, `invalid-bytecode`. Wire-supplied bytecode failed
  structural or deny-list checks.
* *Dynamic class definition* — `Invalid class definition: missing-magic`,
  `invalid-version`, `invalid-shape`, `trailing-bytes`. The class-definition
  payload did not pass file-format validation.

[cols="2,1,3,3", options="header"]
|===
|Reason or message shape |Subsystem |Typical cause |Fix

|`Lambda bytecode rejected: site=%s, reason=security-config-missing, denied=%s`
|Allowlist
|An application class arrived as a class-name payload but is not in generated
security config or the manual allowlist.
|Annotate the producing class with `@Remote.Allowed` or `@PortableType`, run
the Maven or Gradle generator, and package the generated config.

|`Lambda bytecode rejected: site=LAMBDA, reason=dynamic-remote-denied-by-mode`

|A DYNAMIC lambda arrived while security mode was hardened and
`coherence.remote.dynamic.unauthenticated` resolved to `deny`.
|Switch to STATIC lambda serialization or explicitly set
`-Dcoherence.remote.dynamic.unauthenticated=allow`.

|`method-invocation-denied-by-mode`

|A `MethodInvocationProcessor` arrived while security mode was hardened and
`coherence.remote.dynamic.unauthenticated` resolved to `deny`.
|Set `-Dcoherence.remote.dynamic.unauthenticated=allow` only where reflective
method invocation is intentionally exposed, or replace the call with a
purpose-built `@Remote.Executable` processor.

|`script-eval-denied-by-mode`
|Script mode gate
|A `ScriptProcessor` arrived while security mode was hardened and
`coherence.remote.dynamic.unauthenticated` resolved to `deny`.
|Set `-Dcoherence.remote.dynamic.unauthenticated=allow` only where remote

|`Lambda bytecode rejected: site=%s, reason=lambda-target-not-allowed, denied=%s`

|A serialized lambda targets a functional interface that is not marked as a

|`reason=bytecode-references-gadget`
|Bytecode scan
|Generated or supplied lambda bytecode references a deny-listed gadget class or

|`reason=class-name-on-denylist`
|Bytecode scan / MIP reflection

|Remove the deny-listed class from the payload path or reflective MIP target.

|`reason=method-on-denylist`

|A `MethodInvocationProcessor` targets a deny-listed `class#method` pair.

|Graal `PolyglotException` or script error naming a denied Java type

|`reason=native-method-declared`
|Bytecode scan
|Wire-supplied bytecode declares a native method.
|Do not send dynamic bytecode that declares native methods.

|`reason=dynamic-class-forname`
|Bytecode scan
|Wire-supplied bytecode calls `Class.forName` with a non-constant value.
|Resolve the class server-side or remove dynamic class loading from the lambda.

|`reason=invalid-bytecode`
|Bytecode scan / Class definition
|The supplied class bytes are empty, malformed, or cannot be parsed.
|Regenerate the payload with a supported Coherence version and check for

|`Invalid class definition: missing-magic`
|Class definition
|A class-definition payload does not start with the Java class-file magic

|Reject the payload source; resend only valid class files.

|`Invalid class definition: invalid-version`
|Class definition
|A class-definition payload uses an unsupported class-file version.
|Build the producing artifact for a Java version supported by the receiving
member.

|`Invalid class definition: invalid-shape`
|Class definition
|A class-definition payload has an unexpected constant-pool, method, or class

|Regenerate the payload and verify client/server version compatibility.

|`Invalid class definition: trailing-bytes`
|Class definition
|A class-definition payload contains bytes after the parsed class file.
|Reject the payload source; resend a clean class definition.

|`ClassIdentity package is not allowed: %s`
|Class identity / Allowlist

|Annotate the producing type or package and regenerate security config.

|`unknown user type: %s. Unregistered POF type ... strict mode`

|`Deserialization of class %s was rejected`

|Compatibility security mode classified a remote executable object that would

|Treat each tuple as migration work: annotate the class with

`executable="true"` entry before setting
`-Dcoherence.security.mode=hardened`.

== Telemetry

Serialization gate decisions are visible through `SerializationGates` MBeans.
ObjectNames include the route, gate, result, reason, and mode tuple, for
example:

[source,text]
----
Coherence:type=SerializationGates,route=GRPC,gate=filter,result=rejected,reason=serialization-allowlist-rejected,mode=prod
----

Lambda bytecode checks also maintain the in-process counter key:

[source,text]
----
coh.lambda.bytecode_check{result=rejected,reason=dynamic-remote-denied-by-mode,site=lambda}
----

Use these counters to identify which boundary is rejecting traffic before
loosening any runtime property.

Live remote executable enforcement checks in hardened security mode maintain:

[source,text]
----
coh.executable.policy_check{reason=<OperationReason>, role=<SerializationRole>, result=allowed|rejected, mode=<runtime-mode>}
----

For Extend `InvocationService`, the tuple uses `reason=INVOKE` and
`role=EXTEND_PROXY`. `MethodInvocationProcessor` and `ScriptProcessor` use
`reason=PROCESS_ENTRY` and `reason=SCRIPT_EVAL`, respectively. Remote
`MapTrigger` installation uses `reason=TRIGGER` and `role=EXTEND_PROXY`.
Topic subscriber filter/extractor installation and persisted replay use
`reason=EVALUATE_FILTER|EXTRACT` and `role=TOPICS`. Cache data-plane
processor, aggregator, filter, extractor, and comparator installs through
Extend, REST, and gRPC use
`reason=PROCESS_ENTRY|AGGREGATE|EVALUATE_FILTER|EXTRACT|COMPARE` and
`role=EXTEND_PROXY|REST|GRPC`. Coherence Concurrent executor task and callback
installs use `reason=CONCURRENT_TASK` and `role=CONCURRENT`. Live tuples may also include
`sub_reason=policy|mode_gate|denylist|replay_drift`; the tag is additive and
callers must not assume a closed set. Successful policy checks use
`sub_reason=policy`; mode and deny-list sub-reasons are emitted only for
refusals. Topic replay under `warn-allow` records
`result=allowed,sub_reason=replay_drift` to make migration drift visible.

Remote executable policy shadow checks in compatibility security mode maintain:

[source,text]
----
coh.executable.policy_check{result=would_reject, class=<FQN>, reason=<OperationReason>, role=<SerializationRole>}
----

This counter is emitted only by `DefaultRemoteExecutablePolicy.enforce(...)`.
It tells you which remote executable classes would be rejected after migration
to hardened security mode. The `mode` tag is intentionally absent from these
shadow tuples, while `class` is included to make per-class dry-run diagnostics
possible. It does not measure serialization allowlist or lambda bytecode
readiness; validate those gates by running the workload under
`-Dcoherence.security.mode=hardened` in a non-production environment. Topic
subscriber replay records one `would_reject` tuple per compatibility shadow;
install-time dynamic shadows can record policy and mode-gate tuples because
replay has no dynamic mode-gate analog.
